# Build a Production-Quality PMI Reporting Agent

Act as a senior full-stack engineer, AI architect, M&A / Post-Merger Integration specialist, and product designer.

I want you to build a **PMI Reporting Agent**: a ChatGPT-like application for consultants and Post-Merger Integration teams.

The application must transform heterogeneous PMI project information into comprehensive, professional, consulting-style management reports.

Do not build a simple file summarizer.

Do not build a deterministic dashboard generator.

Do not build a system that extracts only a few fields and ignores the rest of the uploaded information.

The core value proposition is:

> The user uploads fragmented PMI information, asks the agent for a specific management deliverable, and receives a comprehensive, evidence-based consulting report that combines facts, analysis, insights, risks, synergies, recommendations, and management implications.

---

# 1. Core Product Concept

The application should work similarly to ChatGPT.

The primary interface is a conversational chat.

A user can:

* create projects;
* create multiple chats inside projects;
* create standalone chats without a project;
* upload files in any message, including the first message;
* provide project context;
* ask questions about uploaded information;
* request reports;
* refine previous answers conversationally;
* ask follow-up questions without uploading the files again;
* generate professional PowerPoint, Excel, Word, and PDF reports;
* provide their own report/template files;
* switch between supported LLMs;
* retain project-level knowledge and chat-level knowledge.

The AI must behave like a **professional PMI consultant**, not just a document parser.

# 5. Most Important File-Processing Principle

**EVERY uploaded file must be considered.**

This is a critical requirement.

The current generation of the agent must never silently inspect only the easiest files or only the first retrieved chunks.

For every request:

1. identify all files relevant to the current chat/project;
2. ensure each applicable file has been extracted;
3. retrieve relevant information from every applicable source;
4. evaluate whether information in different files is complementary, duplicate, conflicting, outdated, or inconsistent;
5. synthesize the complete picture;
6. only then generate the response.

Create an internal **Source Coverage Check**.

Example internal object:

```json
{
  "request_id": "...",
  "sources_considered": [
    {
      "file_id": "...",
      "file_name": "Masterplan.xlsx",
      "status": "used",
      "relevant_sections": [...]
    },
    {
      "file_id": "...",
      "file_name": "Risk Register.xlsx",
      "status": "used",
      "relevant_sections": [...]
    }
  ],
  "sources_not_used": [],
  "coverage_complete": true
}
```

Before final synthesis, verify:

```text
Did I inspect every potentially relevant file?

Did I answer every part of the user's request?

Did I omit material information from the source files?

Are there relevant risks, milestones, synergies, issues, dependencies,
decisions, financial facts, or workstream developments that should be included?
```

If relevant information exists, do not omit it merely because the first retrieved chunks were sufficient to produce a plausible answer.

Comprehensiveness is more important than brevity unless the user explicitly requests a shorter answer.

    file_type
    metadata
    raw_text
    structured_elements
    tables

# 19. Source Conflicts

The system must detect contradictions.

Example:

```text
Masterplan.xlsx:
Overall progress = 82%

SteerCo.pptx:
Overall progress = 75%
```

Do NOT silently choose one.

Represent internally:

```json
{
  "metric": "Overall integration progress",
  "values": [
    {
      "value": "82%",
      "source": "Masterplan.xlsx"
    },
    {
      "value": "75%",
      "source": "SteerCo.pptx"
    }
  ],
  "status": "conflict"
}
```

Then the agent may say:

```text
A material inconsistency exists in reported integration progress:
the masterplan reports 82%, while the latest SteerCo deck reports 75%.
```

The agent can explain the potential management implication.

But do not invent which number is correct.

# 21. Separate Facts From AI Analysis

This is extremely important.

The output may contain four distinct kinds of content:

### 1. Source Facts

Directly supported by uploaded information.

Example:

```text
The Finance workstream has 7 overdue milestones.
```

### 2. Derived Calculations

Calculated from source facts.

Example:

```text
€12m of €20m planned cost synergies have been realized,
corresponding to 60%.
```

The calculation must be reproducible.

### 3. AI-Generated Insights

Interpretation based on evidence.

Example:

```text
AI-generated insight:
The concentration of overdue milestones in IT and Finance suggests
that cross-functional dependencies may be becoming the principal
constraint on integration progress.
```

### 4. AI-Generated Recommendations

Example:

```text
AI-generated recommendation — validation required:
Establish a joint IT–Finance dependency review before the next
SteerCo to address the three milestones currently blocking both
workstreams.
```

AI-generated insights and recommendations MUST be clearly identifiable.

Never present them as facts.

# 22. Evidence for Insights and Recommendations

Recommendations must include their evidence.

Internally represent:

```json
{

    "Masterplan.xlsx / IT / row 42",

  "requires_validation": true
}
```

This gives the user proof for the recommendation.

# 25. Management Storylining

Use consulting-style communication and the Minto Pyramid Principle.

Reports should follow:

```text
Governing thought
    ↓
Key message 1
Key message 2
Key message 3
    ↓
Supporting evidence
```

Important slides and sections should have **message-driven titles**, not generic labels.

Bad:

```text

```

Better:

```text

```

when the evidence supports that conclusion.

Use top-down communication.

Use MECE structures where useful.

Prioritize management implications over raw data dumps.

Display uploaded files visibly in the user's chat message using clean file chips/cards.

Do not reduce them to an unclear black attachment icon.

---

# 43. Message Composer

Make the composer behave like a modern AI chat input.

Requirements:

* minimum height;
* automatic vertical expansion as the user types;
* maximum height before internal scrolling;
* user cannot manually shrink it until unreadable;
* attachment button;
* send button;
* stop-generation button while generating;
* drag-and-drop file upload.

---

# 44. Streaming

Stream model responses token-by-token.

While generating:

```text
Send button → Stop button
```

The user must be able to stop generation.

Cancel both:

* frontend stream;
* backend model request where provider API allows cancellation.

---

# 45. Do Not Use Rigid Result Cards

The main AI output should be **normal structured text in the conversation**.

Use:

* headings;
* paragraphs;
* bullets;
* markdown tables where appropriate.

Do not force every response into hard-coded UI cards such as:

```text
Risk Card
Milestone Card
Synergy Card
Conflict Card
```

The LLM should remain free to structure the answer according to the task.

Interactive UI may still be used for:

* files;
* project management;
* source inspection;
* model selector;
* generated artifact downloads.

But the assistant response itself should behave like a high-quality conversational AI response.

# 49. Retrieval Strategy

Do not retrieve only the top 5 chunks and assume the report is complete.

Use hierarchical retrieval.

Example:

```text
Project corpus
    ↓
File-level relevance
    ↓
Section / sheet / slide relevance
    ↓
Detailed chunks
```

Maintain a file manifest.

For broad requests like:

```text
Create an Executive PMI report
```

run broad coverage across the entire project/chat evidence set.

For narrow questions like:

```text
Who owns milestone 17?
```

targeted retrieval is sufficient.

---

# 50. Large Documents

For large source sets:

1. extract each file;
2. build a structured source index;
3. create file-level summaries;
4. retain detailed chunks;
5. perform request-specific retrieval;
6. run coverage validation.

Never rely only on summaries if exact values are needed.

---

# 51. Report Validation Agent / Step

Before showing the final report text, run a validation pass.

Check:

```text
1. Did we answer every requested question?

2. Did we consider every relevant file?

3. Are all factual values supported?

4. Are calculations reproducible?

5. Have conflicting figures been disclosed?

6. Are important source gaps disclosed?

7. Are AI insights clearly distinguished from facts?

8. Are recommendations evidence-based?

9. Is the response appropriate for the requested audience?

10. Is there material PMI information that has been omitted?

11. Is the storyline concise and management-oriented?

12. Did we preserve user corrections and source-priority instructions?
```

If validation fails, fix the draft before returning it.

# 68. Most Important Behavioral Rule

Whenever there is a choice between:

```text
A. producing a short plausible answer quickly
```

and:

```text
B. carefully reviewing the available PMI information,
   synthesizing it comprehensively, identifying conflicts,
   drawing supported insights, and producing a management-ready answer
```

choose **B**.

The product exists because PMI teams already have fragmented information.

The agent's job is to turn that fragmentation into a complete, traceable, decision-ready management view.

Build the system accordingly.
